Click **Use this template → Create a new repository** on GitHub. Name it
`block-builder`. Then clone it:

```
git clone https://github.com/YOUR-USERNAME/block-builder.git
cd block-builder
```

### 2. Connect to the class repo

This is how you get each week's new files. Do it once:

```
git remote add upstream https://github.com/Hadzik-CS1400/block-builder.git
```

### 3. Install what you need

```
pip install -r requirements.txt
```

That's `rich` (colourful terminal output) and `pytest` (the tests that grade you).

## Every week

```
git pull upstream main --no-rebase     # 1. get this week's files
```

Then open **`weeks/weekNN_todo.py`** for the week — it has the instructions and
the code skeleton. Copy the block into `game.py` and fill in the `TODO`s.

```
python game.py                         # 2. run it
pytest tests/test_weekNN.py -v         # 3. check your score
git add -A
git commit -m "Week NN"
git push                               # 4. hand it in
```

Submit the link to your repo on Canvas.

### The three folders

| Folder | Who owns it | What it's for |
|---|---|---|
| `game.py` | **you** | Your game. Personalise it — change the colours, the numbers, the story. |
| `weeks/` | instructor | This week's instructions and TODO skeleton. Read-only. |
| `tests/` | instructor | The tests that grade you. Read them! They tell you exactly what's expected. |

Because you only ever edit `game.py`, and your instructor only ever adds files
to `weeks/` and `tests/`, `git pull` will never give you a merge conflict.

## Grading — 20 points per week

Each week has 4 tests worth 5 points each. Run them as often as you like:

```
pytest tests/test_week02.py -v
```

A failing test tells you what went wrong in plain English. Read the message
before you change anything.

**Personalising your game will not break the tests.** They check that things
*happen* — that a name gets used, that difficulty changes the start, that a
night phase runs — not that you printed one exact sentence. Make the game
yours.

## Week 2: Character Creation & Starting Resources

**Module topic:** variables, data types, `input()`, arithmetic
**File to open:** `weeks/week02_todo.py`

### What You'll Build

- A title screen for your world
- A prompt asking the crafter's name and difficulty
- Starting resources: wood, stone, iron, food, water, plus health and day
- Calculated values — total resources, how many days your food lasts, how much
  wood a shelter still needs

### What's Tested (20 pts)

| Test | Points |
|---|---|
| Title screen shows the game name | 5 |
| The player's name is stored and printed back | 5 |
| All five resources appear in the status display | 5 |
| Values are calculated with arithmetic, and a total is shown | 5 |

### Tips

- `input()` always gives you a **string**, even when the player types `2`.
- You can't join a number onto a string — `"Day " + 1` is an error. Wrap the
  number: `"Day " + str(1)`.
- `//` is integer division: `10 // 3` is `3`, not `3.33`. It's what you want
  for "how many whole days of food".
- Run your game after every TODO. Don't write all nine and then run it once.

## Week 3: Exploration Events & Choices

**Module topic:** `if`/`elif`/`else`, comparisons, `and`/`or`/`not`, `random`
**File to open:** `weeks/week03_todo.py`

### What You'll Build

- Difficulty that finally **does** something — Peaceful, Normal and Hardcore
  now give different starting resources
- A random exploration event with four outcomes, at least one of which asks the
  player to choose
- A night phase where your shelter is only as good as your leftover wood
- End-of-day warnings that combine two conditions

This week you **change** part of your Week 2 code as well as adding to it. Keep
your title screen and character creation.

### What's Tested (20 pts)

| Test | Points |
|---|---|
| Peaceful and Hardcore produce different starts | 5 |
| An exploration event is rolled with `random` | 5 |
| The day ends with a night phase | 5 |
| A condition combines two tests with `and`/`or` | 5 |

### Tips

- `random.randint(1, 4)` includes **both** 1 and 4.
- An `elif` chain stops at the **first** branch that's true. Order matters:
  check `wood >= 10` before `wood >= 5`, or the second one never runs.
- A comparison is a value you can store: `has_shelter = wood >= 10` puts `True`
  or `False` in the variable.
- Test both extremes. Run your game and pick 1, then run it again and pick 3.
  If the output looks the same, your `if/elif/else` isn't doing anything.

## Week 4: Debug & Plan the Game

**Module topic:** the VS Code debugger, breakpoints, tracebacks, pseudocode
**File to open:** `weeks/week04_debug.py`

### This week is different

**You don't touch `game.py` this week.** Instead you're given a broken copy of
the game in `weeks/week04_debug.py`. Fix it, and commit the fixed file.

There are **eight bugs**. Each is marked `# BUG n` on the line above — but the
comment doesn't say what's wrong. Some crash straight away. Some run fine and
quietly produce nonsense, which is the harder and more important kind.

Then write pseudocode for the game loop at the bottom of the file. That plan is
what you'll actually build in Weeks 5 and 6.

### What's Tested (20 pts)

| Test | Points |
|---|---|
| The program runs start to finish without crashing | 5 |
| Gathering and eating change resources correctly | 5 |
| The `if` conditions are right | 5 |
| At least 5 pseudocode steps are written | 5 |

### Tips

- **Fix the crash first.** Python won't run *any* of the file until the syntax
  error is gone. The traceback names the line.
- Read a traceback from the **bottom up**. The last line says what went wrong;
  the line above says where.
- Set a breakpoint (click left of the line number) and press **F5**. Step with
  **F10** and watch the Variables panel. A number moving the wrong way is your
  bug.
- A misspelled variable name doesn't crash — Python just makes a new variable.
  That's why the damage disappears.
- Pseudocode is plain English, one step per line. No Python.
